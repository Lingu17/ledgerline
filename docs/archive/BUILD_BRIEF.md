## Product
An operational reconciliation workbench for a small international software company. Deposits -> deterministic initial plan -> ask payer's agent when ambiguous -> cryptographically verify signed evidence -> revise plan -> apply action or require approval -> reconcile per currency. The distinguishing demo is a suspected duplicate becoming customer credit after verified evidence, while a different customer's invoice claim is rejected.

## Domain requirements
- Persistent invoices, deposits, allocations, credits, partial receivables, refund operations, approvals, evidence, audit events, policies and currency balances.
- Six deposits across USD/EUR/GBP: two clean, one short, one unknown with malicious cross-customer claim, one apparent duplicate really an advance credit, one true duplicate requiring approval. Scenario dates relative to demo clock. Six or more realistic invoices as needed, avoid fixture inconsistency.
- Reconciliation with exact references + customer + currency. No auto-matching on amount alone. Handle split reference, fee tolerance, partial payment, duplicate ambiguity, missing ref, wrong currency. Never allocate twice or overpay invoice. Track applied amount separately from remaining/unapplied.
- Actual payer MCP server exposing explain_payment, callable via MCP transport, not just a function named MCP. Signed canonical JSON claims with Ed25519 per customer public key registry; bind deposit, customer, currency, amount, invoice, reason, expiry. Check signature, freshness, exact deposit and ownership/amount. Reject foreign invoice, expired, changed amount, tampered signature. Signed proof is evidence, not unconditional authority. Demo agents are explicitly local simulations.
- Approval hash over immutable amount, currency, destination, operation, deposit and evidence version. Revalidate at execution under a DB transaction. Mutation invalidates old approval. Per-deposit durable unique operation lock, stable request IDs, no duplicate debit on retry or concurrent calls. Pause switch prevents all money-out including pending operations; matching can continue. An ambiguous network response remains pending/requires reconciliation, not failed/safe to resend.
- Refund state machine includes pending/processing/sent/paid/cancelled/failed; SENT is not final. Do not mark refund completed or remove liability before confirmed finality. Idempotent provider execution and retry reconciliation.
- Treasury preserves configured source reserves, accounts for existing target wallet cash and obligations, converts only deficit. Quote expiry and single-use, no reuse. Show obligation deadline and before/after balances. Do not sum currencies without a displayed valuation rate.
- Conservation per currency: deposits = allocations + credits + refunds paid + refunds reserved/pending + unapplied. Separate initial wallet balances, expenses/fees and FX legs; no mixed-currency totals pretending to be accounting equality. Balanced journals if feasible. Audit export includes operation IDs, checks and decisions.
- Webhook HMAC over timestamp + raw body; timestamp skew limit, constant-time verification and unique event dedupe persisted transactionally. Reject malformed events. No unprotected money actions if deployed: documented operator auth, CSRF/origin posture; local demo can use restrictive local bind and origin checks. Persist policy and pause across restart.
