# Codex review findings — first pass

These are source-review findings to reproduce with regression tests. Do not treat this list as proof of a passing application.

1. **FX finality (critical):** treasury.execute_conversion starts with status='settled' and never reads res.status. A successful API response with SCHEDULED, CANCELLED or OVERDUE will be posted as settled cash. Respect actual provider status; post cash only upon verified SETTLED. Add a reconciliation path for pending conversions.
2. **Concurrent/in-flight FX reservation (critical):** execute_conversion claims only the quote; another quote for the same obligation can book before the first settles/commits journal movements. Persist source reservation and target pending coverage under BEGIN IMMEDIATE, count them in positions/deficits, and prevent two outstanding operations funding the same deficit. An ambiguous conversion must continue holding its reservation and must not permit another quote to book the same money.
3. **Immediate rejected transfer result:** submit_operation reloads op, calls _post_cash_out (which changes detail), then calls _apply_status with the stale op dict. If the returned result is terminal failed/cancelled, _apply_status does not see cash_out_posted and may fail to reverse the wallet debit. Reproduce with a provider returning a failed result directly and assert journals/cash remain correct. Refresh op or pass correct state before applying status.
4. **Overpayment evidence:** initial matching allocates payable invoices and asks the agent about the excess, but pending_agent_questions and record_agent_answer use the full deposit amount. Applying a verified answer can try to allocate/credit the entire amount after partial allocation. Handle the unapplied portion explicitly or safely escalate; never return a 500 or leave the deposit stuck when evidence arrives.
5. **Signed validity interval:** evidence.verify checks expiry vs now and maximum TTL but not expires_at > issued_at. Reject zero or negative validity intervals; keep a regression test. Validate customer identity against the deposit/asked agent in the workflow boundary too.
6. **Exact money input:** money.to_minor should reject non-finite, negative and boolean values with a controlled MoneyError. Currently NaN/Infinity can escape as unrelated ValueError/OverflowError, and negative input becomes negative minor units. Check the API boundary rejects bad values without 500 errors.
7. **Official webhook payload shape (critical integration):** webhooks._parse_deposit only accepts data.object. Official deposit.settled examples have deposit fields directly under data (https://www.airwallex.com/docs/developer-tools/webhooks/listen-for-webhook-events/deposits). Support and test the documented flat data shape, plus nested shape only if needed for compatibility. Current parser also assumes payer_name instead of the current deposits payer.name structure. Validate received_at and nonempty provider id, handle malformed data/list types as controlled 400. Do not make mocks silently match an invented payload shape.
8. **Windows connection cleanup:** LocalBank uses `with self._conn() as c`, which does not close a sqlite3 connection; it only commits/rolls back. Independent TemporaryDirectory cleanup failed with WinError 32 until gc.collect(). Make _conn a contextmanager with finally close (or use contextlib.closing) so tests/reset/shutdown do not leak file handles.
9. **Do not spend pending FX proceeds (follow-up to #2):** early reservation fix adds fx_in_pending into free_after_commitments, which is also used to choose source currencies. Pending incoming currency is forecast coverage, not spendable cash. Keep available source surplus based on settled wallet cash minus holds/reserves/commitments/outbound reservations. Separately subtract pending target coverage when calculating whether another conversion is needed. Regression: pending EUR proceeds + later small EUR deposit must not permit an outbound EUR conversion that breaches settled EUR reserve. Mark pending coverage clearly in UI.
10. **Negative lookup is not finality:** treasury.sync_conversion currently releases the reservation and marks failed when find_conversion returns None after an ambiguous submission. A missing query result is not affirmative cancellation/rejection and can reflect a delayed/incomplete lookup. Keep the ambiguous operation reserved and visibly requiring reconciliation unless the provider reports a definitive terminal failure. Never permit a fresh quote/request to replace an unknown conversion based only on one missing lookup. Also treat unexpected raw/internal status as unknown/processing rather than failure and reserve release.

Codex independently reproduced #9/#10 after the first reservation fix: injected ProviderAmbiguous on conversion creation, EUR free_after_commitments reported 0 although settled source surplus was -451500 minor units, and find_conversion(None) changed the ambiguous operation to failed with needs_reconciliation=0. These follow-up findings were added after the original eight; re-read the current file before declaring review complete.
